# Схема метаданных контента (frontmatter)

**Статус:** зафиксировано с Alex, июль 2026. Применено ретроактивно ко всем 17 существующим файлам в `knowledge/`. Все новые файлы должны создаваться сразу с этим фронтматтером.

## Зачем

До этого момента весь контент в `knowledge/` был читаемым markdown без машиночитаемых полей — годится для человека, но не для загрузчика в Qdrant (нужно парсить произвольный текст регулярками, что хрупко). Ниже — минимальная YAML-схема сверху каждого файла, которая даёт лоадеру структурированные поля напрямую, а тело файла остаётся текстом для эмбеддинга.

## Формат

```yaml
---
id: kebab-case-slug              # уникальный внутри всего проекта, использовать как ID точки в Qdrant
title: "Человекочитаемое название"
category: history | restaurants | transport | nature | services | auto
subcategory: свободная строка     # museum | cemetery | landmark | cafe | street-food | summer-cafe | dental |
                                   # tram | train | bus | terrenkur-collection | byuvet-collection | ...
status: draft | needs_review | ready   # готовность контента к публикации в боевую RAG-базу
partner_status: none | candidate | confirmed | null   # null — неприменимо (история, транспорт, природа)
address: "ул. ..., N"             # ОБЯЗАТЕЛЬНО для мест из ветки «где поесть» — без адреса место не попадает на сайт, см. примечание 6; для остальных категорий пока допускается null
booking: true | false             # необязательное, по умолчанию false — показывать ли заявку на столик, см. примечание 7
coords: null                      # [lat, lon] — НЕ заполнять вручную, см. примечание ниже
phone: "+7 ..." | null
hours: "свободный текст" | null   # часы работы сложные (перерывы, сезонность) — не структурируем в MVP, см. примечание
price: "свободный текст" | null
tags: [tag1, tag2]
food_types: [завтрак, кофе, десерт, комплексный обед, ужин, шашлык, хинкали, пиво]  # необязательное, только для еды — см. примечание 5
photos: [photos/file1.jpeg]       # относительно папки файла, пусто если фото нет
updated: "2026-07"                # дата последней проверки фактов (YYYY-MM)
---
```

## Важные технические примечания (для бэкенд-разработки)

1. **`coords` заполняется программно, не руками.** Ручной сбор GPS-координат для каждой точки — избыточная работа при сборе на месте. Правильный путь — геокодировать `address` через API (2ГИС/Яндекс.Геокодер) один раз на этапе загрузки в базу, результат закэшировать. Ручной ввод координат не нужен и не запланирован.

2. **`hours` — намеренно свободный текст, не структура (`{mon: "9:00-18:00", ...}`).** Причина: у реальных объектов КМВ часто нерегулярные паттерны — сезонность (бюветы работают по-разному май–октябрь и в остальное время), технические перерывы (бюветы — 10:00–11:00 и 15:00–16:00), разные дни недели с разными часами (краеведческий музей — по пятницам короче). Структурировать это в MVP — избыточная инженерная работа за отсутствием ROI; строка достаточно хорошо работает и для RAG-поиска, и для показа пользователю. Если понадобится сортировка/фильтр «открыто сейчас» — структурировать эту часть отдельно, когда/если действительно понадобится.

3. **«Коллекционные» файлы — важный источник путаницы при загрузке.** Пять файлов на самом деле описывают НЕСКОЛЬКО точек/маршрутов в одном markdown-документе, а не один объект:
   - `nature/byuvety.md` — 7 бюветов в одной таблице
   - `nature/terrenkury-mashuk.md` — 3 маршрута терренкура
   - `transport/tramvay.md` — 8 трамвайных маршрутов
   - `transport/avtobusy-marshrutki.md` — несколько городских + межгородних маршрутов
   - `transport/elektrichki.md` — расписание по нескольким направлениям

   Для этих файлов `id`/`title` описывают весь документ целиком (например, `id: byuvety-pyatigorska`), а не конкретный бювет. **Решение, которое нужно принять на бэкенде:** либо (а) индексировать файл целиком одной точкой в Qdrant — плохо для точечных вопросов вида «когда работает трамвай №3», либо (б) на этапе загрузки программно разбивать такие файлы на под-чанки по строкам таблицы — тогда у каждого бювета/маршрута будет свой чанк с собственными метаданными. Вариант (б) правильнее для качества ответов, но требует парсера markdown-таблиц, а не универсального сплиттера. Это уже согласуется с решением в `CLAUDE.md`: «Расписания — структурированные данные, не через RAG-поиск, а отдельный обновляемый источник» — то есть для транспорта в любом случае нужен отдельный структурированный источник (JSON/CSV/БД-таблица), а не markdown-чанк. Файлы `transport/*.md` в текущем виде — черновик для человека и источник для будущей структурированной таблицы, но не финальный формат для бота.

4. **`status: ready` не означает «опубликовано».** Это флаг «факты проверены, можно грузить в боевую коллекцию» — используется как фильтр в пайплайне загрузки, чтобы черновики (`draft`) не попадали в продакшн случайно.

5. **`food_types` — необязательное поле, добавлено для ветки «где поесть» (июль 2026, из работы над чат-гидом на сайте).** Гид не подставляет заведение сразу, а сначала уточняет тип еды: **завтрак · кофе · десерт · комплексный обед · ужин · шашлык · хинкали · пиво**. «Комплексный обед» — именно формат готового обеда за фиксированную цену, а не «поесть днём»: ставить его заведению можно только если это подтверждено, иначе человек придёт за комплексным обедом и не найдёт его. Поле нужно, чтобы место попало в нужный список; без него заведение в подбор по типу не попадает (сайт сообщает об этом в отчёте сборки). Заполнять только по фактически известному меню — если меню не зафиксировано, лучше оставить пусто, чем угадать. Категория без единого заведения показывает честную пустоту («в базе пока нет»), а не подмену близким вариантом.

6. **Без `address` место не попадает в базу сайта (зафиксировано с Alex, июль 2026).** Сборка `scripts/build-data.mjs` пропускает такие файлы и печатает их списком. Причина: гид не должен вести человека туда, где сам не уверен, что оно находится, и расстояние считать не от чего. Alex добавляет адрес и фотографию сразу при добавлении места, так что это не ограничение, а проверка. Адреса, взятые из интернета без сверки на месте, отмечаются в файле комментарием прямо во фронтматтере (см. `grot-lermontova.md`, `nekropol.md` и т.п.) — это не то же самое, что адрес, подтверждённый фото с места.

7. **`booking` — показывать ли заявку на столик.** По умолчанию `false`. Ставится `true` только там, где бронь осмысленна (ресторан с ограниченным числом столов) и партнёр на неё согласился. Кофейням не ставится: столики там свободны всегда, и заявка только раздражает. Телефон на карточке в интерфейсе не показывается по той же причине — человеку перед выходом нужны часы работы, а не номер.
